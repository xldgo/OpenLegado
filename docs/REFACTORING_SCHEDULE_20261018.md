## 1. 执行顺序

按「收益明确且风险可控 → 编排整理 → 结构性大改（按对应证据决定）」三段推进：

```
Phase 1  小范围边界整理          ← 范围明确、可验证、风险相对可控
Phase 2  UI 编排拆分             ← 提升可测性，接口不变
Phase 3  结构性大改（先核查）    ← 按 SCH-M 的对应测量或缺陷证据决定是否执行
```

这是常规整理的推荐顺序，不是所有任务的硬依赖链。构建测量与风险核查可独立安排；
若确认崩溃、资源泄漏、状态损坏或错误信息丢失，按影响及时立项，不等待整个 Phase 2 完成。

## 2. 并行性判定规则（保留为分析）

### 可并行 —— 必须**同时**满足

1. 文件与接口改动无冲突；不能仅按是否处于同一目录判定
2. 契约协作明确；涉及 FFI 时先冻结契约，不能各自覆盖共享绑定
3. 工作区、构建与生成产物已隔离；合流时统一生成和配套验证，正式产物替换串行执行
4. 不争用需要独占的验收设备或可变素材
5. 无依赖顺序

### 需要隔离或串行集成的情形

| 类型       | 原因                                                        |
| -------- | --------------------------------------------------------- |
| FFI 契约变更 | 同一工作区的生成绑定与 native 替换不能并发写入；隔离分支可分别开发，合流时统一生成和验证 |
| 跨轨共享文件   | `bridge/`、`domain/contracts/`、`data/` 与 `features/` 同一批被改 |
| 依赖顺序     | 后一步需要前一步产物                                                |
| 改公共层     | 公共接口变更可能影响下游，需核对调用方与集成顺序；仅共同依赖 core 不构成禁止并行的依据 |
| 全局路由/装配  | 多个任务同时修改路由表或装配文件时需串行集成；调用方多本身不等于必然冲突 |
| 共享测试基建   | 同时修改 `native_reader_layout.dart` 或共享测试产物时需隔离或串行集成 |

> **当前执行遵守单代理**，本节仅用于未来并行时的边界预判。

## 3. Phase 1 · 小范围边界整理

范围明确、验证直接、风险相对可控。**建议从这里开始。**

### SCH-R2a · 缓存仓储收口（拆三项，逐项保留原语义）

| 子项    | 动作                        | 目标仓储                                     | 必须保留的语义                                    |
| ----- | ------------------------- | ---------------------------------------- | ------------------------------------------ |
| R2a-1 | 配置前缀查询 | `CacheRepository` | 固定 `config:%` 匹配；不新增 deadline/TTL 过滤；坏行跳过并保留原告警行为 |
| R2a-2 | 章级标记删除 | `CacheRepository` | `sameTitleRemoved:{bookUrl}:` 前缀中的 `%`、`_`、`\` 按原规则转义，避免跨书误删 |
| R2a-3 | 按时间查询待清理书籍，并删除对应章节缓存 | **`CacheBookRepository`**（非 `CacheRepository`） | 查询与删除均使用 `cached_at < before_timestamp`；查询行解码失败返回错误，不跳过坏行 |

**R2a-3 不能并入 `CacheRepository`** —— 它是章节缓存的生命周期查询，语义与通用 KV 缓存不同。

**事务与失败边界**：当前整书/按时间清理是多条语句依次执行，没有统一事务回滚保证；
前一步成功、后一步失败时可能留下部分已清理状态。本批只封装查询与写入，不附带新增事务、
改变执行顺序或宣称失败全部回滚。若要事务化，另立行为变更任务。
通用 `CacheRepository.get` 现有 TTL 判定不变，不将它套用到配置批量查询或章节时间清理。

### SCH-R2b · 清理调用点

限定以下调用点改为使用 R2a 的仓储方法；函数名为定位依据，行号随提交变化：

- `rust/legado-ffi/src/api/config_api.rs` 的 `get_all_config`：配置前缀查询。
- `rust/legado-engine/src/reading_service/cache.rs` 的 `clear_book_cache`：删除章级标记。
- 同文件的 `clear_cache_before`：查询待清理书籍、按时间删除章节缓存、逐书删除章级标记。

**前置：R2a 完成。**

**验收**：上述列明操作由相应仓储封装；固定前缀、通配符转义、时间边界、坏行处理、
多语句执行顺序及中途失败的原有结果有行为回归覆盖。已有覆盖先复用，按实际缺口补充。

不要求全仓 FFI/engine SQL 归零；`clear_cache` 全量清空、`VACUUM/PRAGMA`、
备份及 RSS 等其他 SQL 不在本批范围，若需整理另行立项。

### SCH-R2c · 弹幕 XML 解析下沉

`rust/legado-ffi/src/api/video_api.rs` 的 `parse_video_danmaku` 当前不访问 IO 或数据库，
可独立迁移其解析逻辑。实施前核对调用方、模块依赖与既有回归，不以注释作为安全性证据。

**验收**：`quick-xml` 从 `legado-ffi/Cargo.toml` 移除；函数迁入 `legado-book` 或 `legado-parser` 并有单测。

### SCH-F1b · Dart 错误边界整理（合并原 SCH-X2）

当前 features 有 27 个文件直接导入 `bridge/ffi.dart`，多处 `_mapError` / `_errMsg`
直接读取 `BridgeError.message`。原 SCH-X2 与本项合并为一次完整的 Dart 边界整理，
不先统一辅助函数再重复迁移调用方，也不依赖书单导入任务 SCH-X1。

- 数据适配层负责将桥接异常转换为领域错误，保留当前可见消息、错误分类及取消语义。
- 领域层定义错误，不引用 FRB 生成类型；UI 复用展示映射，不直接判断 `BridgeError`。
- 逐个检查导入用途；若存在错误类型以外的生成类型，先明确对应领域映射再移除依赖。
- 保持 Rust 签名、FRB 生成绑定不变，通常不需要 codegen；发现必须改跨语言契约时单独登记。

**验收**：桥接到领域错误的转换及 UI 展示映射各有明确归属；`lib/src/features`
不再直接导入 `bridge/ffi.dart` 或判断 `BridgeError`。验证真实错误消息、普通异常、
取消与 Mock 路径的行为，不以源码字符串检索替代行为回归。

## 5. Phase 3 · 结构性大改（**先核查，后决定**）

> 构建性能改造依据 M-1/M-2 的测量；错误与安全修复依据 M-3/M-4 的实际缺陷证据。
> 实例生命周期及深层模块先核对已有实现和具体痛点，不以不相关的构建数据作为前置。
> 无对应缺口则不执行；风险核查发现的明确问题可按严重性提前处理。

### SCH-M · 测量与风险核查（可独立安排）

| 编号  | 测量项                                                            | 用途                                                  |
| --- | -------------------------------------------------------------- | --------------------------------------------------- |
| M-1 | 增量构建耗时：`legado-core` 改动后各下游 crate 的重编耗时与失效范围                   | 决定 SCH-R1 是否值得                                      |
| M-2 | 依赖失效范围：若拆出 `legado-domain`，统计有多少 crate 会**同时**依赖 core 与 domain | 决定拆分收益（若多数 crate 两者都依赖，收益有限）                        |
| M-3 | 审查生产可达 panic 的触发条件、捕获边界、错误返回、锁与状态恢复；另核对相关 unsafe/原生边界风险 | 决定 panic 与资源安全修复范围；排除测试，不能因 FRB 已捕获而忽略请求失败或状态恢复问题 |
| M-4 | 错误载荷现状：`LegadoError` 各 String 变体在生产路径上丢失的底层错误信息                | 决定 SCH-R3a 的载荷设计                                    |

### SCH-R1 · `legado-core` 拆 crate（**候选，非起点**）

- **规模口径**：不沿用混入测试的初版总行数。测量时列出固定模块清单与提交 SHA，分别统计生产代码和测试；行数仅作辅助，不能直接推导构建收益。
- **决策依据**：M-1 + M-2。若拆出后多数 crate 仍同时依赖 core 与 domain，则收益有限，应放弃或改为更小的边界调整
- 若执行：保留 `error.rs`、`models/`、`crypto.rs`、`regex_safe.rs` 等真正基建；迁出状态机与服务类模块

### SCH-R3a · 错误载荷调整（**不是添加注解**）

`rust/legado-core/src/error.rs` 现状：`Io(#[from] std::io::Error)` 与\
`Serialization(#[from] serde_json::Error)` **已隐含 `#[source]`**（初版称「0 个 source」不准确）。\
待核查的是**确有底层错误却被转成 String 的生产路径**；只承载业务消息、
没有底层错误对象的变体，不强制添加 source 或更改载荷。

**方向**：调整错误**载荷**（让变体承载源错误），而非仅加 `#[source]` 注解。\
**依据**：M-4。

### SCH-R3b · panic 安全（**审查生产可达路径**）

初版「FFI 无 panic 防护、需给所有入口包一层」的**前提错误**：\
FRB 2.13 运行时对同步、普通及异步任务**均已提供 panic 捕获**。

**修订后范围**：

- 不再给所有 FFI 入口重复包装
- 只审查 **生产可达** 的 `unwrap` / `panic!`（排除测试模块，初版计数混入大量测试）
- 对已被 FRB 捕获的 panic，检查请求失败是否可理解、锁中毒及部分操作状态是否可恢复、资源是否释放
- 分别检查 FRB 捕获不覆盖的 abort、UB 及其他原生执行边界；不把 `unwrap` 检索当作完整 unsafe 审计

**依据**：M-3。确认的稳定性问题按影响及时修复，不以 Phase 2 全部结束为前提。

### SCH-R3c · `EngineHolder` 验收目标重写

初版「槽位 ≤3」缺乏依据。`EngineHolder` 的多个 `OnceLock` **不等于多个独立引擎** ——\
初始化时会把已有能力接入**同一个** `EngineContext`。

`EngineContext::in_memory` 已支持同进程独立实例，现有测试覆盖实例资源隔离、
任务取消和根实例释放；`engine_holder.rs` 也有局部 Holder 的重复初始化与关闭回归。
先核对这些实现与证据，再决定是否存在需要整改的缺口，不将既有能力重新列为未实现。

**核查与必要补缺目标**：

1. **实例隔离**：复核现有独立 EngineContext 的数据库、网络、任务等能力归属与释放，仅补实际缺失的行为覆盖。
2. **初始化一致性**：复核已有失败/重复/并发初始化与开库前能力接续，确认符合现有契约。
3. **资源生命周期**：核对端口停止、实际任务退出与 TaskGroup 关闭的现有证据，按缺口修复或补测。

默认 FFI 宿主仍通过进程级 Holder 暴露一个根实例，这是宿主选择，不等于 EngineContext
不能多实例。若需要正式 FFI 支持切库、关闭后重建或多个默认宿主，另立需求与契约任务；
本项不擅自引入这些行为。没有确认缺口时只记录核查结论，不强制修改代码。

### SCH-R4 · 深层模块拆分

`legado-fetcher/src/web_book.rs`（7,917）、`legado-js/src/host_api/quickjs_impl.rs`（7,811）、\
`legado-parser/src/analyze_rule.rs`（4,802）—— 按**具体痛点**立项，不按行数。\
若当前无明确维护痛点，可维持现状。

## 7. 风险与遗留
